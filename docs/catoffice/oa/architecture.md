# CatOffice OA · 架构设计

> 状态：**规划 v0.1**（只规划、不编码）。本文定义 OA 服务端的模块化架构、
> 引擎复用方式、身份模型、部署形态与安全基线；功能边界见
> [product-plan.md](product-plan.md)，接口契约见 [contracts.md](contracts.md)。

## 1. 总体形态

```
                    ┌──────────────────────────────┐
 钉钉/企微/LDAP ───▶ │  连接器层（单向入优先）        │
 外部 CRM/工单  ◀──▶ │  webhook 入站/出站            │
                    └──────────────┬───────────────┘
                                   │
        ┌──────────────────────────▼───────────────────────────┐
        │              CatOffice OA 服务端（独立仓库）           │
        │  ┌──────────┐ ┌──────────┐ ┌─────────┐ ┌──────────┐  │
        │  │ 身份 M0  │ │ 审批 M1  │ │ CRM M1  │ │ 任务 M1  │  │
        │  └──────────┘ └──────────┘ └─────────┘ └──────────┘  │
        │  ┌──────────────────┐  ┌─────────────────────────┐   │
        │  │ 文档归档 M1       │  │ 管理控制台 M0            │   │
        │  └──────────────────┘  └─────────────────────────┘   │
        │  模块间只经内部 API / 事件总线通信，禁止跨库直读        │
        └──────────────────────────┬───────────────────────────┘
                                   │
        ┌──────────────────────────▼───────────────────────────┐
        │  引擎层：主仓 packages/* 以 npm 依赖消费               │
        │  docx-engine（服务端模板套版 / 签发留痕 / 公文）        │
        │  audit（哈希链审计，与桌面端 C1 同构）                  │
        │  contracts（@catoffice/contracts，双仓共享 schema）    │
        └───────────────────────────────────────────────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │ 桌面端（主仓）：工作台 + 文档桥 │
                    │ manifest 驱动，无 OA 业务代码  │
                    └──────────────────────────────┘
```

两条铁律：

1. **模块可拆**：每个 M1+ 模块是独立部署单元（独立进程 / 容器），只依赖
   M0 底座；「底座 + 任一单模块」必须能独立跑（进 OA-0 验收）。
2. **引擎不改**：OA 仓不 fork 主仓引擎包，一律 npm 依赖；引擎缺口回主仓
   提交（保持上游回挑能力）。

## 2. 技术选型（建议，立项时复核）

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 服务端运行时 | Node.js（TS） | docx-engine 等引擎包是纯 TS，同进程直接跑；团队栈一致 |
| Web 框架 | Fastify（或 axle 对齐桌面端 mock 服务器的惯例） | schema-first、生态成熟 |
| 数据库 | PostgreSQL（每模块独立 schema 或独立库） | 单文件部署可用嵌入式（PG 内嵌或 SQLite 起步，接口不变） |
| 对象存储 | 本地盘 / S3 兼容 / WebDAV 三后端抽象 | 归档模块的部署弹性 |
| 异步 / 事件 | 进程内事件总线起步；跨模块用 Postgres LISTEN/NOTIFY 或轻量队列 | 不引入 Kafka 级重依赖，内网部署友好 |
| 前端（OA Web / 控制台） | React + `packages/ui` 设计令牌 | 与桌面端同设计语言 |
| 全文检索 | PG 全文 + 中文分词扩展起步 | 中小内网规模够用；ES 不进默认栈 |
| 认证 | 设备码流（复用 catspark 模式）+ OIDC/CAS（M2） | 与桌面端同构 |

## 3. 模块化与可拆性设计

### 3.1 依赖规则

```
身份(M0) ← 审批(M1) ← 任务(M1 的审批联动)
   ▲  ← CRM(M1) ← 归档(M1)
   └── 控制台(M0，依赖所有已装模块的清单)
```

- 所有模块依赖身份（用户 / 权限），**反向禁止**：身份模块不 import 任何
  业务模块。
- 模块间通信只走内部 API（契约化）与事件总线（如 `approval.completed`、
  `doc.archived`）；禁止跨模块直读数据库表。
- 未装模块的行为：依赖方按「能力缺失」降级（如审批未装时 CRM 的「发起
  会签」按钮不出现），不报错。

### 3.2 部署单元

- 每模块一个容器镜像 + 一份 compose 片段；`docker compose up` 按所选
  模块拼装（基础 = 底座 + 一模块；全家桶 = 全部）。
- Helm chart（OA-1 后）与离线包（政务档）同构生成。
- 模块注册：启动时向底座注册模块清单，`/api/manifest` 由底座聚合输出
  （contracts.md 第一节）。

## 4. 身份与权限模型

- **联邦优先**：LDAP / AD / 钉钉 / 企微通讯录单向同步入（只读），本地不
  成为密码权威；自维护用户仅作无外部身份源时的兜底。
- RBAC 两级：模块级（谁能用 CRM）与操作级（谁能签发、谁只用印）；
  审批流中的角色由流程定义引用组织角色解析。
- 会话：设备码颁发长期 refresh + 短时效 access；桌面端与 Web 端同流。
- 审计归属：全部业务事件带 actor 落审计（见第 7 节），与桌面端 C1 的
  `actor` 字段语义对齐，服务端汇聚后按人查询。

## 5. 文档链路（OA 的心脏）

### 5.1 服务端模板套版（无桌面端在线也成立）

```
模板（docx，含占位域/公文要素） + 数据（表单/CRM 对象/webhook 入参）
  → 服务端调 docx-engine 套版（纯 TS，Node 进程内）
  → 产出正式 docx（字节级合规、可被 Word/WPS 打开）
  → 存档 + 版本记录 + 审计
```

- 这是「OA 单独部署」时对 WPS/Word 用户的完整价值：预览（LibreOffice
  headless 或仅元数据视图起步）+ 标准格式导出 + 流程留痕。
- 公文场景直接复用主仓 M5 成果：GB/T 9704 版心 / 红头 / 印章弧形字 /
  主题词版记。

### 5.2 文档桥（桌面端增强）

流程与安全约束见 [contracts.md](contracts.md) 第三节。架构要点：

- 桥文件流：OA 存储 → 短时效签名下载 URL → 桌面端本地临时副本 →
  编辑 → 用户确认 → `PUT` 回传（新版本）→ 审计。
- 版本策略：回传永远是**新版本**，不覆盖历史；冲突（他人在编辑）由
  桥会话登记检测并提示。
- OA Web 端的「用办公猫打开」按钮 = `catoffice://open` 深链 + 桥 token
  预取，桌面端未安装时降级为 Web 预览。

### 5.3 签发留痕

- 审批意见 / 签发人 / 时间戳写入文档正文指定域（公文要素位），形成
  「谁在何时批了什么」的文件内证据，与流程库里的记录互为备份。
- 用印：印章弧形字占位（桌面端 M5 能力）+ 用印审批记录；不伪造公章图，
  真章物理盖印后的扫描归档走 OCR 管线。

## 6. 数据与存储

- 每模块独立 schema（或独立库），共享仅限身份 id 引用。
- 文档正文永远以标准 OOXML 存储为主真相，**不发明内部文档格式**；
  派生数据（检索索引、预览图、抽取的任务）全部标记为可重建缓存。
- 备份：PG 常规备份 + 对象存储版本化；归档模块提供导出为「目录结构 +
  标准文件」的整库带出能力（不锁客户数据）。

## 7. 安全与合规基线

| 域 | 要求 |
| --- | --- |
| 传输 | 内网全链 HTTPS（客户自签支持）；桥 token 短时效单文档 |
| 审计 | 与桌面端 C1 同构的哈希链 JSONL（`@catoffice/audit` 复用），服务端汇聚各终端上报（对应桌面 oa-plan W0.4 事件） |
| 等保 | 桌面端 compliance-plan 里「服务器侧控制项属于部署方」的口径，在企业版/OA 自建后转为**我们的建设义务**：身份鉴别、审计、入侵防范按二级预置，三级配合测评 |
| 隔离网 | 默认不出网；连接器全部显式启用；无任何外联遥测（对齐 C2 `TELEMETRY_DISABLED`） |
| 国密 / OFD | 跟随桌面端 C4/C5 决策（OA-3），不提前自造容器 |
| 权限 | 模块 + 操作两级 RBAC；文档访问走归档模块 ACL，桥 token 单文档授权 |
| 威胁模型 | OA Web 是内网敌对前端（桌面宿主按敌对处理）；webhook 入站校验签名；模板上传是攻击面（引擎解析需资源限额） |

## 8. 可观测与运维

- 结构化日志（不含文档内容，红线同审计）+ 健康端点 per 模块。
- 控制台展示：模块启停 / 同步源状态 / 存储水位 / 审计查询 / 哈希链校验。
- 升级：每模块独立镜像版本，底座先行；schema 迁移单向向前，回滚 = 重装
  旧版 + 数据备份（内网交付不承诺在线降级）。

## 9. 仓库与交付切分

| 仓库 | 内容 | 发版节奏 |
| --- | --- | --- |
| 主仓（本仓） | 引擎包、桌面端、`@catoffice/contracts` | 引擎随桌面月度 |
| OA 仓（新） | 服务端各模块、OA Web、控制台、部署工件 | 模块独立发版 |
| 契约 | `@catoffice/contracts`（zod schema + OpenAPI 生成）双仓依赖 | 变更走两仓同步评审 |

e2e：主仓以 mock OA（契约 mock-first，同 catspark 惯例）测工作台与桥；
OA 仓以契约测试对齐；双仓联调走 `CATOFFICE_OA_BASE` 直连。

## 10. 风险与对策（架构侧）

| 风险 | 对策 |
| --- | --- |
| 模块拆分带来分布式复杂度过早化 | 单机 compose 内仍为同机多容器；跨模块通信从进程内总线起步，接口不变再外化 |
| 服务端跑 docx-engine 的资源与稳定性 | 套版是确定性转换（非编辑会话），进程池 + 资源限额；压测进 OA-1 验收 |
| 身份联邦质量参差（各 LDAP / 钉钉字段乱） | 同步层做字段映射与冲突策略，首版只读单向，规避回写泥潭 |
| 与桌面端发版耦合 | 契约包版本化；桌面端按「零 OA 业务代码」铁律天然解耦 |
