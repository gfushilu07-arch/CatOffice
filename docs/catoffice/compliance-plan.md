# 合规与安全开发方案（等保 / 审计日志 / 上传同意 / 国密）

> 状态：**规划**。本文档覆盖四个相关话题：等保 2.0（二级/三级对标）、本地安全
> 审计日志、AI 数据与日志上传的用户同意体系、国密算法。目标部署语境是政务
> 内网/信创环境——所有设计以"默认不出网、显式授权、可审计、可撤回"为原则。
>
> 执行顺序（见文末）：C1 审计日志 → C2 上传同意体系 → C3 会话锁定与剩余信息
> → C4 SM3 → C5 国密加密探针 / OFD 立项。

## 一、等保对标：技术要求 → 本项目映射

等保认证本身是测评流程（定级备案 → 建设整改 → 测评），代码侧能做的是把
二级/三级的技术要求预置成产品能力。按 GB/T 22239 对桌面应用有实际约束力的
控制项逐条映射：

| 控制项 | 要求要点 | 现状 | 缺口 | 对应工作项 |
| --- | --- | --- | --- | --- |
| 身份鉴别 | 口令复杂度/传输保护/登录失败处理 | CatSpark 设备码登录（HTTPS）；文档口令 agile 加密 | 会话超时自动锁定 | C3 |
| 安全审计 | 覆盖每个用户、审计重要事件、记录不可篡改、可查询 | **无** | 审计日志本体 | **C1（最大缺口）** |
| 数据保密性 | 传输加密 | HTTPS | 存储加密算法可选国密 | C4/C5 |
| 数据完整性 | 检测重要数据完整性 | 保存即全量重写（天然完整） | 审计日志自身防篡改 | C1 |
| 剩余信息保护 | 存储空间释放前清除 | 恢复副本机制已有 | 临时文件清理策略 + 文档化 | C3 |
| 入侵防范/恶意代码 | 最小安装/漏洞修补 | 桌面端基本不适用 | 测评时文档化说明 | — |

**明确不做**：网络设备/服务器侧的控制项（属于 CatSpark 服务端与部署方）。

## 二、C1：本地安全审计日志（先做——它是 C2 的数据源）

### 事件模型

追加式 JSONL（一行一事件），按天分文件存放于
`userData/audit/YYYY-MM-DD.jsonl`：

```jsonc
{
  "ts": "2026-09-03T10:21:33.456Z",   // ISO UTC
  "actor": "local",                    // 登录体系接入后为用户标识
  "action": "doc.export.pdf",          // 事件类型（见下表）
  "target": "D:/docs/预算.docx",       // 相对语义的目标（文件路径/打印页数等）
  "detail": { },                       // 动作相关附加字段（不得含文档内容）
  "prev": "sha256-of-previous-line",   // 哈希链：防篡改、可验证完整性
  "hash": "sha256(prev + canonical-json-of-this-entry)"
}
```

### 记录的事件（第一版清单）

| action | 触发点 | detail 约束 |
| --- | --- | --- |
| `doc.open` | 打开成功 | 文件大小、是否加密文档 |
| `doc.save` | 保存成功 | 新增/修改/删除字数（不记内容） |
| `doc.export.pdf` / `doc.export.image` | 导出成功 | 页数 |
| `doc.print` | 打印 | 页数、打印机名称 |
| `doc.password.set` / `doc.password.remove` | 文档口令变更 | — |
| `doc.permission.change` | 编辑限制/权限变更 | 模式 |
| `ai.session.start` / `ai.session.end` | AI 会话起止 | 是否线上模式、模型 id（**不含 prompt**） |
| `settings.privacy.change` | 上传同意开关变化 | 新状态 |
| `app.start` / `app.quit` | 应用起止 | 版本号 |

**红线**：任何事件不得携带文档内容、AI prompt/回复文本、口令哈希。
审计日志记"谁在何时对哪个文件做了什么"，不记"内容是什么"。

### 防篡改

- 逐行哈希链（`prev` + `hash`）：任何事后删改会断链，校验工具可定位断点。
- 文件系统层：日志目录写入后不再重写旧文件；轮转按天自然发生。
- 测评加分项（可选，C6）：日志同步写入一个只追加的旁路存储（如独立的
  append-only 文件 + 定期摘要行），测评时演示"单点篡改可被发现"。

### 工程落点

- 新包 `@catoffice/audit`（纯 TS，无 Electron 依赖；渲染/主进程均可 import；
  Electron `userData` 路径由调用方注入）。
- 主进程统一写入（渲染进程经 IPC 转发），避免多写者竞争。
- 性能：写路径是追加快照（fd 常驻 + append），单事件 <1ms；绝不阻塞保存。
- 设置页"安全审计"分区：查看日志、导出、校验完整性（哈希链走查）。
- 测试：事件写入/哈希链验证/篡改检测/轮转/IPC 通路；mock userData。

## 三、C2：AI 数据与日志上传的同意体系

### 分层同意（不做一揽子弹窗）

| 层 | 内容 | 默认 |
| --- | --- | --- |
| T1 | **AI 对话内容上传**（prompt/回复/附件内容进入云端处理） | 关，首次使用线上 AI 时弹窗 opt-in |
| T2 | **崩溃/错误日志上传**（脱敏后的错误堆栈，剥离文档内容） | 关，opt-in |
| T3 | 匿名使用统计（GA4） | 关（构建期不注入密钥时该能力整体不存在） |

### 关键行为

- **时机**：安装时不弹。首次调用线上 AI（`isMockMode() === false` 且未登录
  mock）时弹 T1 同意框；T2/T3 在设置页开启。
- **版本化**：同意记录 = `{ t1: { version, ts }, t2: {...}, t3: {...} }`，存
  `app-settings.json`；隐私政策版本升级 → 对应层重新询问。
- **撤回随时生效**：设置页开关；撤回 T1 后线上 AI 直接不可用（提示重新
  开启），撤回 T2/T3 后立即停止上传并清空待传队列。
- **技术卡点**：`createElectronTransport` 是全部线上 AI 调用的单通道——在此
  检查 T1 同意，未同意直接返回结构化错误（UI 提示"需开启 AI 数据授权"）。
  **mock 模式永不受此门控**（信创隔离部署承诺）。
- **上传通道**：CatSpark 新端点 `/api/telemetry/*`（`catspark-integration.md`
  增补契约；mock 路由先行）。上传内容 = 本地审计日志的 AI 相关子集（仅
  `ai.session.*` 事件 + 用户显式提交的错误报告），**不是审计日志全量**。
- **政务部署**：`CATSPARK_TELEMETRY_DISABLED=1` 环境变量整体禁用上传面
  （连同意弹窗都不出现），对应隔离网络交付。

### 工程落点

- 同意状态存取进 `app-settings`；同意弹窗组件（复用 modal 惯例）；
  transport 门控；`/api/telemetry` mock + 客户端；设置页"隐私"分区。
- 测试：门控拦截/放行、同意版本化、撤回清队列、隔离部署变量、mock 路由。

## 四、C3：会话锁定与剩余信息保护（小刀）

- 用户可配置的空闲超时（默认 15 分钟）：到时锁定 UI（重输文档口令/系统
  凭据解锁），正在进行的 AI 流取消。
- 退出时清理：自动保存恢复副本的保留策略与"打开后清除源文档明文临时文件"
  的既有行为做一次审计梳理，形成测评文档页。

## 五、C4/C5：国密

### C4：SM3（先做，最轻）——✅ 已完成（2026-09-04，见执行进度表）

- 用途：审计日志哈希链可选国密模式（`CATOFFICE_AUDIT_HASH=sm3`）、未来 OFD 的摘要。
- 选型定案：**仓内纯 TS 实现**（`@catoffice/audit` 的 `sm3.ts`）——不引 npm
  国密包（供应链审计负担），不占 Rust sidecar（audit 包零运行时依赖契约）。
- 测试：GB/T 32905 标准向量（`abc` → `66c7f0f4...`、示例 2）+ OpenSSL(3)
  交叉参考 5 组（块边界/跨块/长消息/UTF-8）。

### C5：SM4 文档加密 + OFD 立项——SM4 加密 ✅ 已完成（2026-09-04，见执行进度表）；OFD 立项仍待决策

- **互操作探针先行**：WPS 的国密加密 OOXML 容器格式需要真实样本验证
  （与 ECMA-376 agile 的做法一致——先探再定）。自造容器是兜底不是首选。
- **OFD**（GB/T 33190）：政务交付趋势要求，规范强制国密签名（SM2/SM3）。
  做 OFD 必然引入全三件国密。**建议单独立项讨论**：OFD 导出（渲染管线
  已有 PDF 导出，OFD 是版式 XML 另一目标）vs 只做国密加密——前者战略
  价值大但工程量数倍。
- 决策点：信创线的真实客户需求强度。若 OFD 进规划，C5 并入 OFD 项目。
